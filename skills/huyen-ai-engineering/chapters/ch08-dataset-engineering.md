# Chapter 8: Dataset Engineering

## Core Idea
Model quality is bounded by data quality: the goal of dataset engineering is to build the dataset that trains the best model within your budget, governed by three criteria — quality, coverage, and quantity (p. 638, 642). As fewer teams can differentiate on models, data becomes the differentiator, and synthetic data plus rigorous verification is how you scale it (p. 638, 662).

## Frameworks Introduced
- **Quality / Coverage / Quantity — the three data curation criteria** (p. 642): cooking analogy — quality = ingredient freshness, coverage = the right mix of ingredients, quantity = how much you need.
  - When to use: every time you design a training set, for any training phase (pre-training, SFT, preference finetuning).
  - How: define what "high-quality" means per the six characteristics below; enumerate diversity axes your users actually exhibit; size the set based on finetuning technique, task complexity, and base-model performance (p. 650).
- **Six characteristics of high-quality data** (p. 643-646): relevant, aligned with task requirements, consistent, correctly formatted, sufficiently unique, compliant.
  - When to use: before creating data, write down what each characteristic means for your task (p. 646).
- **Data-centric AI vs. model-centric AI** (p. 639): improve performance by enhancing data (processing techniques, high-quality datasets) rather than architectures/sizes/training techniques. DataComp-style benchmarks fix the model and compete on datasets (p. 640).
- **Small-dataset probe before big investment** (p. 652-653): finetune on ~50 well-crafted examples first. Clear improvement → more data will help more. No improvement → a bigger dataset will rarely fix it (but check hyperparameters and prompts before concluding).
- **Performance-gain curve for data sizing** (p. 654-655): finetune on 25% / 50% / 100% subsets and plot performance vs. size. Steep slope → doubling data pays off; plateau → it won't. Returns typically diminish (first 1,000 examples +10 points, next 1,000 +5).
- **Progressive finetuning to stretch scarce high-quality data** (p. 654): self-supervised → supervised (legal docs then QA pairs); less-relevant → relevant (tweet sentiment then product sentiment); synthetic → real (synthetic medical records then real ones). Warning: two coordinated finetuning jobs — easy to burn compute for a worse model.
- **Reverse instruction** (p. 677): take existing high-quality long-form content (books, Wikipedia) and use AI to generate the prompts that would elicit it — the response is human, so no response hallucination. Li et al.'s bootstrapping loop: train weak model on seeds → generate instructions for high-quality content → finetune on the result → repeat.
- **Data flywheel** (p. 657): leverage data generated by your own users to continually improve the product. Application data is ideal because it exactly matches the distribution you care about.

## Key Concepts
- **Instruction data**: (instruction, response) pairs for SFT; preference finetuning needs (instruction, winning response, losing response) (p. 640).
- **Annotation guidelines**: explicit definitions of what a good response is and why; needed for both manual and AI-powered annotation, and identical to evaluation guidelines from Chapter 4 (p. 660). Teams like LinkedIn report them among the hardest parts of the pipeline.
- **Data augmentation**: new data derived from real data (flip a cat image) (p. 661).
- **Synthetic data / data synthesis**: data generated to mimic properties of real data (simulated mouse movements); terms often used interchangeably with augmentation (p. 661).
- **Model collapse**: irreversible degradation from recursively training on AI-generated data — probable events get over-represented, rare events forgotten (Shumailov et al., p. 684). Mixing real data with synthetic can avoid it (Gerstgrasser et al., p. 684).
- **Model distillation**: train a small student to mimic a large teacher using teacher-generated data; DistilBERT is 40% smaller, keeps 97% of capability, 60% faster (p. 686).
- **Ossification**: pre-training can freeze weights so they adapt poorly during finetuning; smaller models are more susceptible — with millions of examples, evaluate training from scratch (p. 650).
- **Back-translation**: verify a translation/generation by mapping it back to the source and comparing (p. 673); Llama 3 used it to verify AI-generated code explanations (p. 674).
- **Self-play**: model generates data by playing against itself (OpenAI Dota 2: ~180 years of games/day; AlphaGo) (p. 673).
- **Data lineage**: AI generation obscures where data came from — inherited copyright violations and benchmark contamination become undetectable (p. 685).

## Mental Models
- Think of training data as ingredients: spoiled ingredients (quality), wrong mix (coverage), wrong amount (quantity) each ruin the dish independently (p. 642).
- Use PEFT on more advanced models when data is small (hundreds-thousands of examples); use full finetuning on smaller models when data is large — with 550K examples all models converge to similar performance (p. 651-652).
- Use "aligned with task requirements," not "accurate": a factually correct answer is wrong data if the task demands creativity or conciseness (p. 644).
- People synthesize what they can verify — coding data dominates synthetic training sets because execution makes it functionally verifiable (p. 681). Prefer synthesis targets with programmatic checks.
- Curation is also subtraction: remove data to make the model unlearn bad behaviors (e.g., delete examples with unsolicited rewrites to stop an arrogant chatbot) (p. 642).
- Distillation is not the ceiling: a student can surpass its teacher (Nemotron-4-340B-Instruct beat its 56B-parameter Mixtral teacher) when synthetic data is verified before use (p. 687-688).

## Anti-patterns
- **Large noisy datasets over small clean ones**: 10K crafted instructions beat hundreds of thousands of noisy ones (Yi); LIMA's 1,000 curated examples rivaled GPT-4 in 43% of cases (p. 643).
- **Skipping annotation guidelines and hoping the model figures it out**: risky for most applications; guidelines double as eval guidelines, so the work amortizes (p. 660).
- **Imitating a proprietary teacher for reasoning gains**: imitation models mimic style but fail on factuality and generalization; training a student on solutions it can't derive teaches it to hallucinate answer-shaped text (Gudibande et al., p. 684).
- **Training indiscriminately on self-generated data**: doesn't improve and can degrade the model; only verified synthetic data enabled Llama 3's self-improvement (p. 688).
- **Ignoring duplicates**: repeating 0.1% of data 100x degraded an 800M model to 400M-level performance (Anthropic, p. 693); duplicates also contaminate train/test splits (p. 692).
- **Leaving formatting junk in**: Databricks removed extraneous Markdown/HTML tokens → +20% accuracy and −60% input length (p. 696).
- **Mismatched inference prompts after finetuning**: if training used `burger -->`, then `burger`, `Item: burger -->`, or a trailing space all cause issues (p. 699).
- **Trusting public datasets**: always check license and provenance; a commercially licensed dataset can contain non-commercial-source content (p. 659).

```text
# Prompt-engineering prompt (3-shot, base model) — before finetuning:
Label the following item as either edible or inedible.
Item: burger
Label: edible
Item: car
Label: inedible
Item: mushroom
Label: edible
Item: {INPUT}
Label:

# Finetuning training data — each shot becomes a training example:
| Input        | Output   |
| burger -->   | edible   |
| car -->      | inedible |
| mushroom --> | edible   |
```
- **What it demonstrates**: converting few-shot prompts into finetuning examples — after finetuning, the prompt shrinks to just the input, cutting token cost (p. 697-699).

**Six data-quality characteristics** (p. 643-646):

| Characteristic | Test |
|---|---|
| Relevant | Examples match the task (19th-century legal data is only relevant if the task is 19th-century law) |
| Aligned with task requirements | Annotations match what the task demands (factual, creative, concise, score+justification) |
| Consistent | Two annotators on the same example shouldn't diverge much; needs annotation guidelines |
| Correctly formatted | Remove HTML tags, trailing whitespace, inconsistent casing/number formats |
| Sufficiently unique | Dedup to a task-appropriate tolerance; dupes bias and contaminate |
| Compliant | No PII or policy-violating content per internal/external rules |

**Why synthesize data — five motivations** (p. 662-665): increase quantity (scarce/dangerous domains); increase coverage (edge cases, toxic examples, rare classes, adversarial data); increase quality (AI beats humans at tool-use traces, complex math problems, consistent preference ratings); mitigate privacy (healthcare, insurance); distill models.

**Deduplication methods** (p. 695): pairwise comparison (exact/n-gram/fuzzy/semantic — expensive at scale); hashing (MinHash, Bloom filter — compare only within buckets); dimensionality reduction then pairwise. Libraries: dupeGuru, Dedupe, datasketch, TextDistance, TheFuzz, deduplicate-text-datasets.

**Data quantity factors** (p. 650): finetuning technique (full finetuning needs orders of magnitude more than PEFT/LoRA); task complexity (sentiment classification << financial-filing QA); base model performance (closer to target → fewer examples; opposite of pre-training scaling).

## Worked Example
**Llama 3's synthetic coding-data pipeline with built-in verification** (p. 678-680) — the chapter's flagship synthesis-plus-verification walk-through:

1. **Generate problems**: AI generates a large, topically diverse collection of programming problem descriptions (p. 678).
2. **Generate solutions**: given a problem plus a target language, AI generates a solution; including general good-programming rules and CoT reasoning in the prompt improved quality (p. 678).
3. **Verify statically**: run generated code through parsers and linters to catch syntactic errors (missing imports, uninitialized variables) (p. 678).
4. **Verify dynamically**: run AI-generated unit tests to catch runtime errors (p. 678).
5. **Self-correct**: on any failure, prompt the model to revise, feeding back the problem, faulty solution, and parser/linter/test feedback. ~20% of initially incorrect solutions self-corrected (p. 678, 702). Only examples passing all checks enter the SFT set.
6. **Multiply via translation**: AI translates verified code across programming languages; translations that fail tests are filtered out (p. 679).
7. **Multiply via back-translation**: AI generates explanations/documentation from code, then regenerates code from those explanations; keep the explanation only if the regenerated code is faithful to the original (p. 674, 679).

Result: 2.7M+ verified synthetic coding examples for Llama 3.1's SFT (p. 679). The lesson: every generation step is paired with a programmatic verification step — that pairing, not generation volume, is what made self-improvement work (p. 688).

## Key Takeaways
1. Design data from behaviors backward: decide what you want the model to learn (CoT, tool use, multi-turn), then build data exhibiting exactly those behaviors — and remove data showing behaviors you want unlearned (p. 640-642, 700).
2. Quality and coverage beat raw quantity: a diverse AND high-quality 2,000-example set beats either property alone (Zhou et al., p. 648); task diversity mattered up to ~282 tasks before plateauing (Chung et al., p. 655).
3. Probe with ~50 examples before scaling annotation spend; use subset scaling curves to forecast the value of more data (p. 652-655).
4. Synthesize what you can verify — pair every generation step with functional checks, AI judges, back-translation, or heuristic filters (Self-Instruct filtered repetitive, too-long/short, and input-echo examples) (p. 681-682).
5. Guard against model collapse: mix real data with synthetic, never train recursively on unverified self-generated data, and watch for bias amplification in data feedback loops (p. 684-685).
6. Stare at your data: 15 minutes of manual inspection routinely saves hours; plot distributions by source/annotator/time, compute inter-annotator disagreement, and re-annotate samples yourself to audit trust (p. 690-691).
7. Process in the cheap-first order, never mutate in place, and match inference prompt format exactly to training format (p. 688-689, 699).
